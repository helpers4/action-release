# Design: JSR and crates.io targets

Status: **proposal, nothing implemented.** Decisions marked ❓ need the owner's answer.

## What stays true

The release commit, the tag used as a lock, the two jobs (the `build` job runs project code with
`contents: read`; the `publish` job writes and signs and runs none of it), the dry-run on every
registry before the tag, `resume`, and "the release never rewrites what a human wrote" are
unchanged. A registry becomes a plug-in with four operations:

| Operation | Job | What it does |
| --- | --- | --- |
| `prepare` | build | write the version in the registry's manifest, in the release commit only |
| `package` + `dryRun` | build | produce the artifact, check it, dry-run the publication |
| `isPublished` | publish | ask the registry whether the version is already served (`resume`, `npm-ahead`-like checks) |
| `publish` | publish | authenticate with OIDC and upload |

`registries` takes a list: `npm`, `jsr`, `crates`, `none`; `?` still makes one optional.
Detection proposes the targets (`package.json` → `npm`, `jsr.json`/`deno.json` → `jsr`,
`Cargo.toml` → `crates`) but never publishes to a registry that is not listed.

## Facts (from the registries' documentation and `helpers4/rust`)

- **JSR**: tokenless publishing from GitHub Actions needs `id-token: write` and the repository
  linked in the package settings on jsr.io. `npx jsr publish` packages from the source tree
  (`jsr.json`/`deno.json`: `name`, `version`, `exports`, `publish.include`); `--dry-run` runs all
  checks without uploading. Provenance is generated by JSR itself, only from GitHub Actions. The
  documentation does not describe uploading a prebuilt tarball.
- **crates.io**: trusted publishing is configured per crate (repository, workflow file,
  environment). `rust-lang/crates-io-auth-action` exchanges the OIDC identity for a short-lived
  token; `helpers4/rust` publishes with `cargo publish --locked` using it, after
  `cargo package --locked` and `cargo publish --dry-run --locked`.

## Where "one artifact" holds, and where it cannot

| Target | Artifact built once in `build` | Publish job |
| --- | --- | --- |
| npm | the tarball (unchanged) | uploads that tarball |
| crates | the `.crate` from `cargo package --locked`, attested | ❓ see below |
| jsr | none: JSR packages from sources | checks out the release commit, runs `jsr publish` |

**crates ❓** `cargo publish` repackages from the source tree and, by default, compiles it
(`build.rs`, proc-macros): that is project code in the privileged job, and the uploaded bytes may
differ from the attested `.crate`. Two options:

1. **Upload the prebuilt `.crate` ourselves** to the documented publish endpoint of the crates.io
   web API, with the token of the trusted publishing exchange. Same bytes as attested, no project
   code in `publish`. We own a small client (metadata JSON from `Cargo.toml`).
2. **`cargo publish --no-verify --locked`** in `publish`: no compilation, but the `.crate` is
   rebuilt, so the attestation is about a sibling of what is uploaded.

Recommendation: option 1, falling back to option 2 only if the endpoint proves impractical.

**jsr** is the exception to the golden invariant "the published bytes are the attested bytes": the
invariant becomes "the published sources are those of the release commit" and the attestation
is JSR's own provenance. `jsr publish` does not execute project code; it is pinned by version.

## Versions in the release commit

Placeholder on the branch (`0.0.0`), real version in the release commit:

- `Cargo.toml` (`[package] version`, or `[workspace.package]`), and the root package entry of
  `Cargo.lock` so that `--locked` still passes.
- `jsr.json` / `deno.json` `version`.

A project that already keeps the real version on its branch (as `helpers4/rust` does) gets the
existing `placeholder-version` warning, then switches to the placeholder in its migration PR.

## Checks and failures

- `isPublished` for each registry decides what `resume` still has to do (`planResume` already
  works per registry).
- Preflight: the version already served (`version-published`), a registry ahead of the tags
  (`npm-ahead` generalised), a manifest without `name`/`version`, a crate with `publish = false`.
- Docs: one troubleshooting section per new code.

## Out of scope

Several packages or crates in one release (`helpers4/typescript`, Cargo workspaces with several
published crates): a later design. One package per run, selected by `package`, as for npm.

## What cannot be tested without publishing for real

Both registries only accept a package that exists, under a permanent name (a crates.io name cannot
be freed; a JSR package can be deleted only in limited cases). ❓ Testing the real publication
needs a sandbox name on each registry, created by the owner. Until then, everything up to the
dry-run is testable against fakes and the registries' dry-run commands.

## Migrations this enables

- `mozlz4`, `sqlite-reader`: `npm` + `jsr`.
- `helpers4/rust`: `crates`. Its `api-since.json` updated by `scripts/update-api-since.py` fits
  `prepare` only if the file is listed in `carry`. Its checks (`job-semver`, `compat`, docs) become
  the `checks` job.
- `helpers4/typescript`: needs the multi-package design first.

## Proposed order

1. Refactor npm behind the registry interface, with no behaviour change (the tests stay green).
2. `crates` (dry-run, version and lock rewriting, `isPublished`, publish).
3. `jsr`.
4. Sandbox publications, with the owner's agreement, then the migrations.
